# agent-org

The template for an organization's **org repository**: the one place that says who an organization is, which SOP instance its agents follow, and which repositories hold each capability the fleet relies on — every one pinned to a commit. An agent starts from a single local file that points at an org repository; everything after that is resolved from `org.json`.

This is the template. It validates on its own with example data. An organization creates an instance from it (for example `qwts/qwts-agent-org`) and replaces the examples with real data; the tooling, docs, and CI stay the same.

## The contract

| File | What it holds | Read by |
| --- | --- | --- |
| `org.json` | Identity, the pinned SOP source, and the capability map | Agents resolving the organization; `tools/org.mjs` validates it |
| `governance/repos.json` | The manifest of governed repositories | `tools/repos.mjs`, which also renders the table in `docs/governed-repos.md` |
| `governance/agents.json` | The GitHub App roster: one row per agent identity | `tools/organization-profile.mjs`, which projects it into the profile |
| `governance/organization-profile.json` | The secret-free projection the agent identity runtime bootstraps machines from | `agent-bot bootstrap --profile`, fetched by the machine-setup tooling |

Capability repositories have no pointers or subdomains of their own: a name such as `ci` or `agent-bot` resolves through `org.json` to a repository, a commit, and an entry file. Moving a capability is a reviewed edit of one file.

## Creating an instance

1. On GitHub, **Use this template** to create the instance repository (`<account>-agent-org` by convention; the local `config.toml` names it, so any name works).
2. Fill in `org.json`: `organization.id` and `organization.account`, the SOP instance under `sources.sop`, and one capability entry per repository the organization relies on. Every `ref` is a 40-hex commit SHA; the zeros in this template are placeholders for the shape, not values an instance keeps.
3. Replace the example data under `governance/` with the real manifest and roster, then regenerate the derived files: `node tools/repos.mjs --write` rewrites the table and the profile together.
4. Run `npm run check` and `npm test`. CI runs the same commands on every pull request.

## Validation

| Command | What it checks |
| --- | --- |
| `node tools/org.mjs` | `org.json`: schema version 1, no unknown keys, a non-empty identity, a profile path that exists, the pinned SOP source, and every capability entry — kebab-case name, `owner/name` repo, 40 lowercase hex characters of ref, an entry path inside the repository, a summary. Duplicate keys are reported too. |
| `node tools/repos.mjs check` | `governance/repos.json` and the roster validate, and `docs/governed-repos.md` and the profile are in sync with them. |
| `node tools/organization-profile.mjs` | The profile is the projection of the roster. |
| `npm run check` | All three, in that order. |
| `npm test` | The unit and CLI tests under `tools/tests/`, fixtures included. |
| `npm run lint:markdown` | markdownlint over the docs. |
